Many people now use teams of AI agents. Instead of giving one big job to one agent, they split it into pieces and give each piece to a different agent: one agent writes the code, and another one tests it. Sometimes this works very well, and sometimes the team does worse than a single agent. Most of these teams are built by trial and error. You come up with a protocol, a set of rules for who does what and how the results come together, try it on a few examples and change it until it works.

That is fine if you only need a result and can afford to try. But when you start a big task, you want to know in advance whether your agents will solve it, and if they will, how long it will take and how much it will cost. So we asked: if we split a problem between agents, will the team make progress? How fast? And when does it get stuck?

**Local Work, Global Progress** answers these questions with a convergence theory for teams of agents, joint work with [Peter Richtárik](https://richtarik.org/). We test it with LLM agents that plan routes for warehouse robots. The video above tells the story step by step; this page is its written version, with the main formulas and numbers from the [paper](https://arxiv.org/abs/2610.28286).

## Which tasks need a team

Not every task needs a team. To change a light bulb, you need one person, and nine people around the ladder will not make it any faster. Other tasks split into parts that do not depend on each other. One agent books your flights and another one sorts your email; they can work at the same time, and nobody has to coordinate anything.

The interesting tasks are the ones where splitting helps but the parts depend on each other. A module of a program can pass its own tests and still break the whole program, for example if it sends data in a format that the next module does not understand. In a warehouse, every robot needs a route to its goal, but two robots cannot be in the same place at the same time, so a route that is great for one robot can be terrible for another. Here a team can help a lot, and this is also where teams run into trouble.

## From a task to a function

To guarantee anything, we first have to describe the task in the language of math. In any task, the agents make decisions: in the warehouse, the moves of the robots at every step; in programming, the lines of code. We put all these decisions together and call them $x$, one possible solution. A function $F(x)$ gives every solution a score, and the smaller the score, the better the solution. Solving the task becomes an optimization problem: find the $x$ with the smallest $F$.

The agents do not need a formula for $F$. Usually something can simply tell you the score of a solution, like the tests of a program or a simulator for robots. We call it the **verifier**.

## The robot game

Our first idea was to test this on code, since that is where people use agents the most. But code is built to be split into independent modules. In a small project, a good agent writes its module almost without mistakes, and the modules rarely get in each other's way. Strong conflicts in code show up in big systems, which are very hard to analyze. There is also no single best program: many programs are correct, and to see how good one is, someone has to read it carefully. So with code, we cannot really say how far the agents are from the best solution.

We wanted a task where real conflicts appear already with a few agents and that is easy to analyze, so we chose robots in a warehouse. The floor is a $16\times16$ grid with a few walls, and every robot has a start and a goal. Time moves in ticks. At each tick, a robot moves to a neighboring cell or waits, and it pays one point for every tick until it reaches its goal. Two robots collide if they are in the same cell at the same tick, and also if two neighbors swap cells, because then they pass right through each other. The score adds up the arrival times of all robots and 100 for every collision, and the verifier is a small simulator that plays the plan tick by tick.

The plans are written by a language model, GPT-OSS-120B. It runs no path-finding algorithm: it reads the map as text and writes the moves of every robot itself. With enough robots, it has to think for a while to find a good plan, and every plan is easy to check. Classical algorithms solve this problem exactly, and for us they are useful in another way: they give the best possible plan, so we always know how far the agents are from it.

## One agent, a growing warehouse

We start small: three robots and one agent that plans all of them. For the agent this is easy, and in about half a minute a safe plan is ready (a median of 35 seconds over 120 such searches).

This also gives the first assumption of our model. A proof needs assumptions, and ours should make sense and be checkable on real runs. The first one is that **the agent is smart enough**. It does not have to find the best plan right away, but every try should shrink the distance to the best plan for its robots by at least a fixed share. We write $q(H)$ for the share of the available improvement that an agent finds with $H$ tries.

Then the warehouse grows to nine robots on the same floor, and the simplest option is to give all of them to the same agent. Now the task is much harder. In the agent's plans the robots keep running into each other, and the agent has a hard time sorting it out. We tried several prompts and let the agent change only one route at a time. In the end it managed, but slowly: its mean gap to the best plan falls below 15 only after about 17 minutes.

## Hiring a team

Three robots are easy for one agent, so we hire two more agents and give each of them three robots. Each agent has a small task again, and all three can work at the same time. The solution is now split into blocks, $x=(x_1,x_2,x_3)$. Block $x_b$ holds the moves of agent $b$'s robots, and only agent $b$ can change it.

Blocks give the second assumption: **single blocks can make progress**. As long as the plan is not the best, at least one agent can improve it by changing only its own block, by an amount proportional to the gap. The constant of this proportionality is $\mu$. This is not always true. Sometimes the only way to improve the plan is for two agents to change their blocks together, and we call this a single-block trap. On the robot task, traps are rare, and they show up only at the very end, when a safe plan has already been found.

## Everyone for themselves

At first, each agent could see only its own robots, just like in the small warehouse. Each agent did a perfect job: all of its robots took shortest paths, and they never hit each other. But the whole plan had collisions between robots of different agents, and nobody could fix them. Each agent looked at its own robots, saw a perfect plan and changed nothing, so the plan got stuck.

This was not bad luck. Every run of this team on the first map ended with collisions, although a single agent with all nine robots found plans without collisions. All robots share the same floor, so it is not enough to tell each agent to take three robots from here to there. Each agent also needs to know where the other robots are going.

## The correction

In terms of $F$, each agent has so far scored its plan only by its own robots: when they arrive and whether they hit each other. This is its **local objective** $L_b$. When agent $b$ changes its block from $x_b$ to $u$, the real score changes by $f_b(u;x)=F(x_{-b},u)-F(x)$, where $x_{-b}$ are the other blocks. The agent sees part of this change in its local objective. The rest, here the collisions with other agents' robots, is the **correction** $R_b$:

$$
\underbrace{f_b(u;x)}_{\text{change of }F}
\;=\;
\underbrace{L_b(u)-L_b(x_b)}_{\text{local objective}}
\;+\;
\underbrace{R_b(u;x)}_{\text{correction}}.
$$

With the exact correction, the agent sees the whole change of the real score and optimizes the right thing. In practice we do not give the full correction to the agent, even when we could compute it. Someone has to send it, and every message takes time. The agent's task also gets harder, since it has to look at all the other robots again, and we already saw what happens when one agent thinks about nine robots at once.

The agent does not need all of it anyway. Most possible collisions never happen, so the agent only needs to know about the ones that did. When the verifier finds a collision between robots of two agents, it tells both agents which robots collided, when, and where the other robot will be. After that, a route that hits that robot costs the agent 100 extra points. This is an approximation $\widehat R_b$ of the correction, and the agent searches the corrected objective

$$
\widehat f_b(u;x)=L_b(u)-L_b(x_b)+\widehat R_b(u;x).
$$

  caption="The score splits into the local objectives of the agents (the arrival times of their robots) and the collisions between robots of different agents. For one agent, the change of F is the change of its local objective plus the correction."

Here is a real example from our runs. Robot $r_1$ of one agent swapped cells at tick 11 with robot $r_8$ of another agent, a collision that the verifier had already reported. In round 4, the agent owning $r_1$ gave it another shortest route with the same arrival time. For the agent's local objective, the two routes are the same; only the correction shows that the new one is better. This one change removed the collision and lowered $F$ from 244 to 144, the best possible plan.

The approximation is not perfect. An agent knows only about the robots it was told about, so a new route can hit a robot it has never heard of. The verifier sees this collision and reports it, and the next time the agent can plan around both robots. With every check, the approximation gets a little better.

This brings the last assumption: **the correction is good where it matters**. Surprisingly, it does not have to be good everywhere. The proof only needs it to be accurate for two changes: the best change $u_b^*$ that the agent could make, and the proposal $U_b$ that it actually returns. On a bad route that nobody proposes, it can be completely wrong, and the theory does not care. On the robots this makes a big difference. A uniform bound on the correction error over all routes would exceed $10^4$, while the measured error is zero at the best changes and about 40 at the proposals.

## One round of the protocol

Now each agent can plan its robots and still take the other robots into account. But the agents work at the same time, and in the end we need one plan, so someone has to put their changes together. We call it the **coordinator**. The team works in rounds:

1. At the start of a round, the current plan $x$ is frozen. All agents start from it, and nobody changes it while they work.
2. The agents search in parallel, each one only in its own block. Each agent tries up to $H$ answers and sends the one that looks best under its corrected objective. This is its proposal $U_b$.
3. "Looks best" relies on the approximate correction, which can be wrong, so the verifier checks every proposal separately. It changes only this one block of the frozen plan and computes the real score. How much the score goes down is the **gain** $g_b=\max\{0,\,F(x)-F(x_{-b},U_b)\}$ of this proposal.
4. The coordinator merges proposals into the next plan.

Why not accept all three changes? Because two changes can each be good and still be bad together. Imagine two robots of different agents that both have a shortcut through the same narrow passage. If one robot takes it, it saves time, and so does the other one. But if both take it at the same tick, they collide.

To see which changes can be combined safely, look at how the score is built. It is a sum of small pieces. Each robot adds its arrival time, and this piece depends on one block. A collision between robots of two agents adds 100, and this piece depends on both of their blocks. We draw this as a **dependency graph**: every agent is a node, and two agents are connected if some piece of the score depends on both of their blocks. Then we color the nodes so that connected nodes always get different colors. Agents of the same color are never connected, so their changes cannot get in each other's way, and their gains simply add up. The number of colors is $\kappa$.

The coordinator's rule is simple: in each color, add up the verified gains, and accept the color with the biggest total. The best group is never worse than the average group, so every round keeps at least a $1/\kappa$ share of all verified gain,

$$
F(x)-F(x^+)\;\ge\;\frac1\kappa\sum_b g_b ,
$$

and since gains within one color add up exactly, the score never gets worse. In our warehouse, the robots of any two agents can collide, so the graph is a triangle, $\kappa=3$, and each round accepts the change of one agent. In a warehouse where the first and the third agents work in different parts and their robots never meet, the edge between them disappears, they can share a color, and $\kappa=2$.

## Does it work?

We ran this protocol on the nine-robot warehouse and looked at how far the plan is from the best one over time. The team without corrections got stuck, and its plans kept their collisions between robots of different agents. The single agent's mean gap fell below 15 after about 17 minutes. The team with corrections and the coordinator found plans without collisions in every run and reached the same level after about 9 minutes. Then it kept going, and in the end its plans were better than the single agent's.

## What we can prove

We now have the whole protocol and three assumptions: the agents are smart enough, single blocks can make progress, and the correction is good where it matters. We measure progress with the gap $\Delta(x)=F(x)-F^*$, how far the current score is from the best possible one. The theorem says that, on average, every round removes at least a fixed share $\alpha$ of the gap, up to an error floor:

$$
\boxed{\;\mathbb E\,\Delta(x^K)\;\le\;(1-\alpha)^K\,\Delta(x^0)+\frac{B}{\alpha}\bigl[1-(1-\alpha)^K\bigr],
\qquad \alpha=\frac{\mu\,q(H)}{\kappa}.\;}
$$

The share $\alpha$ is a product of three numbers, one from each part of the protocol. The first, $q(H)$, is the share of the possible improvement that an agent finds in one round; the longer an agent thinks, the larger it gets, and our agents found about two thirds. The second, $\mu$, is how much single blocks can improve the plan compared with the gap. In a single-block trap it is zero, and the theorem cannot promise any progress; on our two maps it was 0.43 and 0.70. The third, $1/\kappa$, comes from the merge rule, and on our maps it is one third. So $\alpha$ is large when the agents are smart, when single agents can make progress and when the coordinator keeps a lot of the work. Without the second term, the gap shrinks geometrically: with $\alpha=1/2$ it halves every round. On a log scale this is a straight line, and in optimization it is called linear convergence.

The second term comes from the errors of the approximate correction. With errors, the theorem cannot promise that the gap reaches zero, only that it falls to a floor of at most $B/\alpha$, where $B$ measures the errors at the two changes that matter: the best change and the proposal. If the corrections are exact, $B=0$, and the gap goes all the way to zero. In our runs, the error at the agents' proposals was about 100 in the first round, one collision that the agents did not know about, and fell to a few units after six or seven rounds. So $B$ gets small quickly, and the floor goes down with it.

Then we checked the theorem on real runs. We measured $q$, $\mu$ and the correction errors in every round of every run and put them into the bound; nothing is fitted to the curves. The bound held in every round of every run, and it goes down together with the real curve. But it stays far above it: by the end, the bound is 30 to 60 times the observed gap.

## Keeping more of the work

The bound is loose because of $\kappa$. With three colors, it assumes the worst case, in which the coordinator keeps only a third of the verified gain in every round. In reality it keeps much more. Often only one agent improves in a round, and then the coordinator keeps all of its gain. We can measure this: in each round $k$, divide all verified gain by the gain the coordinator actually kept,

$$
\kappa^*_k=\frac{\sum_b g_b}{F(x^k)-F(x^{k+1})}\;\le\;\kappa .
$$

We call it the **realized number of colors**. In the worst case it is three; in our runs it was about 1.5 on average.

The same measurement shows how to make the team faster. In most rounds that made progress (79 of 121 on the first map), at least one rejected proposal would also have improved the plan. And the conflicts turned out to be rare. Proposals get in each other's way mostly at the very start, when almost every agent improves and the new routes often collide. As the plan gets better, the parts interact less and less, and near the end they are almost independent. The worst case, where all improving proposals of a round conflict, happened in only 8 of 105 rounds with several improving proposals, 6 of them in the first round. Even changes that interact are sometimes worth combining. In 20 of the 82 rounds that accepted several changes, the changes together gained more than the sum of their gains: each new route alone hits the other agent's old route, but together they do not collide at all.

So we tried a greedier coordinator. Instead of picking one color, it asks the verifier for the score of combinations of proposals and accepts the best one it finds. With three agents, it can simply check all seven combinations. With many agents there are too many, so the coordinator can go step by step: it starts from the best color and keeps adding the proposal that lowers the score the most, as long as some proposal still does. In both cases the best color is one of the options, so every round gains at least as much as with the best color. Our theorem still holds, also with the realized number of colors, and this number is now about 1.2.

In practice this helped a lot. On the first map, the greedier team's mean gap falls below 15 after about 6.5 minutes instead of 9, and across all tasks its whole search is about 30% shorter. Its bound, with the realized number of colors instead of $\kappa$, ends within a factor of 3 to 7 of the observed gap, instead of 30 to 60.

There is one more nice consequence. In a real task, it can be hard to know which parts depend on each other. Then you do not need to build the graph or find the colors at all. The coordinator can simply look for the best combination of proposals in every round, you measure the realized number of colors as you go, and the bound holds with it. This number also shows how tangled a system really is. If it stays close to one, the parts barely get in each other's way; if it is close to the number of agents, almost every change gets in someone's way. So instead of drawing the graph, you can run the team for a few rounds and measure how coupled your task is.

## The warehouse grows again

Then we made the task larger and added a second floor. The second floor looks similar, but the walls stand in other places, and the robots start and finish in other cells. Now there are 18 robots and six agents, three on each floor. Robots on different floors never meet, so the graph is two separate triangles. A triangle still needs three colors, but now each color can hold one agent from each floor, so $\kappa$ is still 3, and with the best color the coordinator accepts two changes per round, one on each floor.

The single agent has to plan both floors at once, and its mean gap gets within 30 of the best plan after about 19 minutes. The team needs about 9 minutes, as with one floor, because the two floors are planned at the same time, and the greedier team about 7. In median, the six-agent team completes its search in half the single agent's time (595 against 1200 seconds) and ends with better plans. The theory works here too: with the realized number of colors, the bound holds in every round and stays within a few times of the observed gap.

## Beyond robots

None of this is specific to robots. Here is how the same recipe works for code. Say we want to build a big system, like the software of a bank. We split it into modules, such as accounts, transfers and cards, and give each module to its own agent. Each module has its own tests, which check what goes in and what should come out, and the whole program has tests too: a customer sends money to a friend, and both balances change correctly.

The verifier is the test suite, and the score $F$ is the number of failing tests, those of every module plus those of the whole program. An agent's local objective is the tests of its own module. The correction appears when a program test fails because of one module, for example one that sends data in a format the next module does not understand. When the verifier sees such a failure, it sends this test to the agent of that module. Now the test is part of the agent's score, and the agent has to fix its module so that it passes its own tests and this one too. Just like with the robots, the agent does not get every test of the program, only the ones its module actually broke. And the coordinator does the same job as before: it checks the changes and merges the ones that work together.

  alt="Three agents with the modules accounts.py, transfers.py and cards.py and their own tests, the program tests below, and a verifier counting failing tests"

/>

People already build systems like this, and sometimes they work. What is new here is the guarantee. If you set up a team this way, you can check our three assumptions on your task: are the agents smart enough, can a single module make progress, and is the correction good where it matters. Then the theorem tells you that progress is linear: every round removes a fixed share of what is left. And if you measure $q$, $\mu$ and $B$ on a few runs, you can estimate how many rounds your task will take, and so how much time and money it will cost, before you spend them. On the robots, constants averaged over 10 runs of the team bound the mean gap of the other 10 runs in every round.

## Results in numbers

- **Corrections make the team work.** The three-agent team finds collision-free plans in all 40 runs on two maps, and its final plans are better and more consistent than those of a single agent. Without corrections, only 2 of 20 runs end with a safe plan.
- **Parallel search alone buys speed, not quality.** Three single agents searching the same plan in parallel are the fastest in median on one floor (about four and a half minutes against seven for the team), but they end with worse plans, and 3 of their 40 runs end without a safe plan.
- **The advantage grows with the task.** On two floors, the six-agent team completes its search in half the single agent's median time (595 against 1200 seconds), and its median final gap is 11 against 22.5.
- **Checked merging pays off.** Accepting the best checked combination of proposals makes the team's search about 30% shorter, and this team is the first to reach a safe plan on every task. Merging all proposals without a check does not help.
- **The theory follows the runs.** With constants measured on the runs, the bound holds in every round of every run. With the realized number of colors it ends within a factor of 3 to 7 of the observed gap.

Two smaller studies test the theory where its constants can be measured or certified exactly: query planning in SQLite, where the correction is learned from the engine's execution counters, and a synthetic task with certified constants.

## Takeaway

So, back to the question from the start: can we guarantee anything when a team of agents splits a task? Yes. The protocol needs two things. Each agent needs to know how its changes affect the others, and someone needs to check the proposals before merging them. Then, under assumptions that can be checked, the theorem tells you how fast the team gets close to the best solution and where it can get stuck. If the coordinator checks combinations of proposals, it keeps much more of the agents' work than the worst case suggests. And before spending millions on thousands of agents, you can measure a few numbers on small runs and estimate what you will get.

The [arXiv preprint](https://arxiv.org/abs/2610.28286) contains the proofs, the learned corrections, the cost of private work and the full experimental protocols. The [GitHub repository](https://github.com/vectozavr/local-work-global-progress) contains the agents, the prompts and the records of every run.
